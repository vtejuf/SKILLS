## 核心理念与总论

### AI 协同开发的本质

AI 协同开发不是"用户提需求、AI 盲目执行"的简单模式，而是一个**双向协作、共同创造**的过程：

```
用户（人类）                    AI（QAgent）
   │                              │
   │  [需求输入] ──────────────>  │
   │  [清晰、具体、有上下文]      │  [理解、分析、设计方案]
   │                              │
   │  <────────────── [方案反馈]  │
   │  [确认、调整、补充]          │
   │                              │
   │  [开发过程] ──────────────>  │
   │  [持续沟通、问题反馈]        │  [执行、报告、等待确认]
   │                              │
   │  <────────────── [进度报告]  │
   │  [验收、迭代、优化]          │
   │                              │
   │  [总结] ─────────────────>  │
   │                              │  [知识沉淀、文档更新]
   │                              │
   │  <────────────── [成果交付]  │
   │                              │
```

### 递归五阶段模型

开发流程采用**递归的五阶段模型**：

```
核心需求
├── 需求理解阶段  ← 基于干净上下文
├── 开发阶段        ← 执行
├── 测试阶段        ← 验证
├── 总结收尾阶段    ← 为下一阶段准备干净上下文
└── 归档阶段        ← 固化知识

每个阶段中的子需求，同样完整经历这 5 个阶段
```

**五个阶段的闭环关系**：

```
         ┌────────────────────────────────┐
         │  需求理解 ──→ 开发 ──→ 测试    │
         │    ↑                    │      │
         │    │                    ↓      │
         │  归档 ←── 总结收尾 ←────┘      │
         │                                │
         └──────── 准备干净上下文 ────────┘
                    ↓
              【下一个需求】
```

理解这个过程的关键在于：

1. **总结收尾的输出 = 下一阶段的输入**：总结收尾阶段整理出的环境信息、交付清单、约束条件，构成了下一阶段（无论是当前项目的子需求还是全新项目）需求理解阶段的**干净上下文**。
2. **避免记忆污染**：如果不经过总结收尾直接进入下一个需求，上一阶段产生的临时信息、失败的尝试、过时的中间状态会残留在上下文中，导致 AI 理解偏差和输入性错误。
3. **递归中的上下文接力**：子需求完成后同样需要收尾 → 为父需求提供更新的上下文，确保整个递归过程中上下文始终是准确、精简的。

**为什么递归？**

1. **可控性**：大需求拆分为小需求，逐个击破
2. **可追溯**：每个子需求的进展清晰可见
3. **可回溯**：出现问题时可以精准定位到具体阶段
4. **可复用**：标准化的流程适用于任何规模的需求

## QAgent 协作要求：对用户输入的期望

### 1. 需求理解阶段

#### 输入要求

✅ **好的需求输入**：
```
"帮我把 https://wiki.xxx.com/?pageId=123 保存为本地知识库，
保存到 d:/project/wiki/ 目录，
这个知识库用于后续的语义检索"
```
- ✅ 明确的目标（保存为本地知识库）
- ✅ 具体的参数（URL、目录路径）
- ✅ 上下文信息（用途是语义检索）

❌ **不好的需求输入**：
```
"帮我保存一下这个页面"
```
- ❌ 目标模糊（保存成什么格式？）
- ❌ 参数缺失（保存到哪里？）
- ❌ 无上下文（后续要做什么？）

#### 对话确认流程

```
用户提出需求
    ↓
QAgent：理解并复述需求
    ↓
用户：确认或调整
    ↓
QAgent：给出初步方案
    ↓
用户：确认或提出修改意见
    ↓
【进入开发阶段】
```

### 2. 开发阶段

#### 持续输入要求

✅ **应该主动提供的反馈**：
- 发现问题及时指出："这个页面的图片没有下载"
- 提出明确要求："希望用 JSON 格式而不是 YAML"
- 给出边界条件："最多处理 100 个文档"
- 提供偏好信息："代码风格要简洁易读"

❌ **应该避免的沟通方式**：
- 消极等待 AI 完成后再验收（发现问题需要返工）
- 模糊的否定（"不对" without "哪里不对"）
- 一次性提出太多修改意见（逐点调整更高效）

#### 决策确认

当 AI 提出技术方案对比时，用户应该：
1. 理解每个方案的优缺点
2. 根据项目实际情况做出决策
3. 明确告知 AI 选择哪个方案及原因

```
QAgent：我们有两个方案实现遍历
  方案A：递归方式（代码简单，但深度难以控制）
  方案B：BFS队列（略复杂，但深度可控）

用户：选择方案B，因为知识库可能有深层嵌套
```

### 3. 测试阶段

#### 测试输入要求

✅ **应该提供的测试用例**：
- 正常场景：常规功能使用
- 边界场景：数据量大的情况
- 异常场景：网络失败、权限不足等

❌ **应该避免的测试方式**：
- 只在理想条件下测试（忽视异常情况）
- 使用模拟数据而非真实环境（发现不了实际问题）

#### 问题反馈格式

✅ **好的问题反馈**：
```
"问题：当文档标题包含特殊字符 # 时，
     JSON 文件解析失败
     复现方式：..."
```
- ✅ 具体的现象描述
- ✅ 复现条件
- ✅ 期望结果

❌ **不好的问题反馈**：
```
"JSON 文件有问题"
```
- ❌ 太模糊
- ❌ 没有上下文
- ❌ 无法定位

### 4. 总结收尾阶段

#### 知识沉淀输入

用户应该：
1. 分享开发过程中的关键决策原因
2. 说明为什么选择某种技术方案
3. 总结遇到的问题和解决思路
4. 提供可复用的经验教训

```
用户：当时选择 JSONL 而不是 SQLite，
     是因为项目部署环境有限，
     不希望引入额外的数据库依赖。
```

### 5. 归档阶段

#### 文档确认

用户应该：
1. 确认文档的准确性
2. 检查约束描述是否清晰
3. 提供补充说明或示例
4. 提出文档优化建议

## 五阶段开发流程详解

### 阶段 1：需求理解

#### 目标
明确"我们要做什么"、"为什么做"、"做成什么样"

#### QAgent 的任务
1. 理解用户需求的核心意图
2. 识别关键约束和边界条件
3. 提出澄清性问题
4. 给出需求分析报告

#### 用户需要提供
1. 明确的目标描述
2. 必要的上下文信息
3. 预期的交付成果
4. 约束条件（时间、资源、技术栈）

#### 输出产物
- 需求分析报告
- 任务拆解清单
- 初步技术方案

#### 质量标准
- ✅ 需求清晰无歧义
- ✅ 约束条件明确
- ✅ 交付成果可量化
- ✅ 双方达成一致

---

### 阶段 2：开发

#### 目标
将需求转化为可运行的代码或可交付的成果

#### QAgent 的任务
1. 设计技术方案（必要时给出方案对比）
2. 编写代码/生成内容
3. 遵循最佳实践和规范
4. 及时报告进度和问题

#### 用户需要提供
1. 技术选型决策
2. 代码风格偏好
3. 持续的问题反馈
4. 必要时的方向调整

#### 开发模式
```
方案设计（需求理解）
    ↓
用户确认
    ↓
实现核心功能（最小可用版本）
    ↓
测试验证（由测试阶段完成）
    ↓
用户验收或提出修改
    ↓
迭代优化
    ↓
完成
```

#### 输出产物
- 可运行的代码
- 配置文件
- 使用文档

#### 质量标准
- ✅ 功能符合需求
- ✅ 代码可维护
- ✅ 有错误处理
- ✅ 有必要注释

---

### 阶段 3：测试

#### 目标
验证交付成果是否满足需求，发现并修复问题

#### QAgent 的任务
1. 编写测试用例
2. 执行功能测试
3. 发现并报告问题
4. 修复验证

#### 用户需要提供
1. 真实的测试环境
2. 典型的使用场景
3. 边界和异常案例
4. 清晰的问题反馈

#### 测试类型

| 测试类型 | 目的 | 示例 |
|----------|------|------|
| 功能测试 | 验证功能正确性 | 基本功能是否正常工作 |
| 边界测试 | 验证极端情况 | 大数据量、空数据等 |
| 异常测试 | 验证错误处理 | 网络失败、权限不足 |
| 集成测试 | 验证模块协作 | 多个功能组合使用 |
| 回归测试 | 验证修改不影响其他 | 新增功能后测试旧功能 |

#### 输出产物
- 测试报告
- 问题清单
- 修复记录

#### 质量标准
- ✅ 核心功能测试通过
- ✅ 边界情况处理正确
- ✅ 有清晰的错误提示
- ✅ 无严重缺陷

---

### 阶段 4：总结收尾

#### 目标
完成交付、更新文档、沉淀知识

#### ⭐ 设计理念：为下一阶段提供干净上下文

**核心思想**：总结收尾不仅是当前项目的结束，更是下一项工作的**上下文准备阶段**。

**为什么重要？**

- 🧠 **防止记忆混乱**：长时间对话后，上下文中会积累大量已完成的临时信息、重复的尝试、失败的历史记录。这些"噪音"会干扰 AI 对新需求的判断。
- 📝 **防止输入性错误**：如果没有清晰收尾，用户在下一个项目可能会使用过时的约束、过时的环境信息，导致需求输入有误。
- 🔄 **支持多项目并发**：当涉及多个项目时，清晰的收尾可以确保每个项目的边界明确，避免混淆。

**实施方法**：

1. **项目状态明确化**：明确提出"本项目已完成"，明确交付物的最终状态
2. **环境信息归档**：将项目特定的环境（路径、配置、依赖）保存到归档文档，而非上下文
3. **清理临时变量**：在代码和文档中移除临时使用的调试代码、测试数据
4. **文档准确性验证**：确保 SKILL.md 等文档与最终交付物一致
5. **知识抽取输出**：将经验教训提取为独立的知识文档（如本文档），而非留在对话中

**示例**：

❌ **不好的收尾**：
```
"好的，功能都完成了，文档也更新了"
```

✅ **好的收尾**：
```
项目已结项：
- 交付成果：download_wiki.py、ragzero_search.py、SKILL.md
- 环境配置：Python 3.8+，依赖 requests, BeautifulSoup4, html2text
- 限制说明：适合 50-500 页文档
- 已归档：开发流程文档（docs/SKILL-AI-Collaboration-Guide.md）
- 上下文清理："本项目已完成，可以开始新任务"
```

#### QAgent 的任务
1. 确认所有功能完成
2. 更新相关文档
3. 提炼可复用经验
4. 总结关键决策
5. **明确项目归档状态**，为下一阶段提供干净上下文

#### 用户需要提供
1. 最终验收确认
2. 文档反馈
3. 补充说明
4. 知识分享
5. **确认项目可以结项**，明确下一阶段的开始

#### 输出产物
- 最终交付物
- 更新的文档（如 SKILL.md）
- 开发总结报告

#### 质量标准
- ✅ 所有需求已实现
- ✅ 文档准确完整
- ✅ 知识已沉淀
- ✅ 用户确认验收

---

### 阶段 5：归档

#### 目标
保存成果、提炼方法论、便于复用

#### QAgent 的任务
1. 提炼可复用模式
2. 生成项目档案
3. 更新最佳实践库
4. 标记可复用组件

#### 用户需要提供
1. 归档范围确认
2. 分类建议
3. 重要程度标记
4. 使用说明

#### 归档内容

| 归档类型 | 内容 | 用途 |
|----------|------|------|
| 代码归档 | 源代码、配置文件 | 后续维护和复用 |
| 文档归档 | SKILL.md、设计文档、测试报告 | 知识传承 |
| 知识归档 | 经验总结、最佳实践、决策记录 | 指导后续项目 |
| 工具归档 | 脚本、模板、检查清单 | 提高效率 |

#### 质量标准
- ✅ 归档完整无遗漏
- ✅ 分类清晰易查找
- ✅ 便于复用
- ✅ 版本管理规范

## 递归迭代与子需求处理

### 递归模型

```
核心需求：构建 Wiki 知识库系统
├── 阶段1：需求理解 ✓
├── 阶段2：开发
│   ├── 子需求：下载功能
│   │   ├── 阶段1：需求理解 ✓
│   │   ├── 阶段2：开发
│   │   │   ├── 子需求：单页面下载 ✓
│   │   │   ├── 子需求：子页面递归
│   │   │   │   ├── 阶段1：需求理解 ✓
│   │   │   │   ├── 阶段2：开发（选择递归算法）
│   │   │   │   ├── 阶段3：测试（发现深度不可控问题）
│   │   │   │   ├── 阶段4：总结（需要重构）
│   │   │   │   └── 阶段5：归档（记录经验）
│   │   │   └── 子需求：引用链接补充
│   │   ├── 阶段3：测试
│   │   ├── 阶段4：总结
│   │   └── 阶段5：归档
│   ├── 子需求：转换功能
│   └── 子需求：索引功能
├── 阶段3：测试
├── 阶段4：总结
└── 阶段5：归档
```

### 子需求拆解原则

#### 1. 独立性
每个子需求应该可以独立完成和测试

✅ 好的拆解：
- 子需求1：单页面下载
- 子需求2：子页面递归
- 子需求3：图片提取

❌ 不好的拆解：
- 子需求1：下载和转换一起做
（两个功能耦合，难以独立测试）

#### 2. 可验证性
每个子需求都有明确的验收标准

✅ 好的子需求：
```
"实现单页面下载功能，
 将 HTML 保存到指定目录，
 验收标准：能够正确保存 test.html 文件"
```

❌ 不好的子需求：
```
"实现页面相关功能"
（无明确验收标准）

#### 3. 优先级
合理排序子需求，先核心后辅助

```
P0（核心）：基础下载功能
P1（重要）：子页面递归
P2（增强）：图片提取
P3（优化）：性能优化
```

#### 4. 依赖关系
明确子需求之间的依赖

```
子需求2（子页面递归）依赖 子需求1（基础下载）
子需求3（图片提取）依赖 子需求1（基础下载）
→ 开发顺序：1 → 2 & 3并行
```

### 递归迭代的实际执行

#### 场景：发现子需求的问题

```
在"子页面递归"这个子需求的测试阶段：
发现问题：递归深度不可控

递归处理这个子需求：
├── 阶段1（理解）：需要控制遍历深度
├── 阶段2（开发）：重构为 BFS 算法
├── 阶段3（测试）：验证深度控制有效
├── 阶段4（总结）：记录递归转 BFS 的决策
└── 阶段5（归档）：保存 BFS 实现经验

完成后，继续执行"子页面递归"的后续阶段
```

## 核心原则与最佳实践

### 1. AI 能力优先原则

**核心思想**：充分利用 AI 的语言理解、逻辑分析和代码生成能力，避免需要人类专家的领域知识。

**应用场景**：
✅ 适合 AI 处理：
- 理解自然语言需求
- 分析代码结构
- 生成标准代码
- 总结文档内容
- 设计技术方案（基于已有知识）

❌ 不适合 AI 处理（需要人类决策）：
- 明确技术选型（需要结合具体环境）
- 决定架构风格（需要团队偏好）
- 最终验收（产品责任）
- 知识领域创新（需要创造力）

---

### 2. 小步快跑原则

**核心思想**：将大需求拆解为小需求，快速迭代，持续验证。

**实施方法**：
1. **MVP 优先**：先实现最小可用版本
2. **增量开发**：逐步增强功能
3. **频繁测试**：每个改动都测试
4. **即时反馈**：发现问题立即调整

**示例**：
```
第1次迭代：MVP
- 实现单页面下载
- 输出为 Markdown

第2次迭代：增强
- 支持子页面递归
- 支持图片下载

第3次迭代：优化
- 改用 BFS 算法
- 增加缓存机制

第4次迭代：完善
- 引用链接补充
- 元数据生成
```

### 3. 需求清晰原则

**核心思想**：用户输入的需求必须清晰明确，包含所有必要信息。

**标准需求格式**：
```
【目标】要实现什么功能
【输入】需要什么参数
【输出】期望什么结果
【上下文】用途和限制
【约束】边界条件
```

**对比示例**：

❌ 模糊需求：
```
"帮我实现一个下载功能"
```

✅ 清晰需求：
```
"帮我实现一个从 Confluence 下载页面的功能

目标：将 Wiki 页面保存到本地，用于构建知识库

输入：
- Confluence 页面 URL
- 本地保存目录

输出：
- Markdown 格式的文档文件
- 图片附件保存到 images/ 目录

上下文：
- 知识库需要支持语义检索
- 文档规模：几十到几百页

约束：
- 需要支持子页面递归下载
- 需要处理内部链接
- 性能要求：单页下载 < 10秒"
```

---

### 4. 持续反馈原则

**核心思想**：开发过程中保持密切沟通，及时发现问题并调整。

**反馈时机**：
- 📌 需求理解后：确认理解正确
- 📌 方案设计后：确认技术选型
- 📌 功能实现后：验收核心功能
- 📌 测试发现后：明确问题描述
- 📌 迭代优化时：提出改进方向
- 📌 总结收尾时：确认文档准确

**反馈质量**：
- ✅ 具体（不说"有问题"，说"哪里有问题"）
- ✅ 有上下文（描述复现步骤）
- ✅ 有期望结果（说明希望如何）
- ✅ 提供建议（如果知道如何改进）

---

### 5. 知识沉淀与上下文管理原则

**核心思想**：每次开发都是知识的积累，要系统性地记录和归档；同时，总结收尾阶段必须为下一阶段准备干净的上下文，防止记忆污染和输入性错误。

**沉淀内容**：
1. **决策记录**：为什么选A不选B
2. **问题与解决**：遇到的问题和解决思路
3. **最佳实践**：可复用的经验和模式
4. **工具模板**：检查清单、代码模板

**上下文管理（关键！）**：
1. **明确项目边界**：每个项目完成后，明确结项和交付清单
2. **环境信息归档**：项目特定的配置、依赖、限制条件保存到文档而非上下文
3. **清理临时信息**：移除调试代码、测试数据、废弃的设计方案
4. **提取知识输出**：经验教训形成独立文档，避免留在对话中污染上下文
5. **为下一阶段准备**：整理项目的最终状态、约束条件、适用场景，作为下一阶段的输入参考

**归档层级**：
```
L1（个人笔记）：快速记录想法
L2（项目文档）：项目的完整文档（如 SKILL.md）
L3（知识库）：跨项目可复用的方法论（如本指南）
L4（模式库）：标准化的解决方案模板
```

**特别提醒**：
- ⚠️ 不要跳过总结收尾阶段，直接进入下一个项目 → 会导致上下文混乱
- ⚠️ 不要保留过时的约束信息在新项目中 → 会导致输入性错误
- ⚠️ 不要让失败的尝试和临时方案残留在对话中 → 会导致 AI 误判

---

### 6. 版本控制与提交规范原则

**核心思想**：每个开发阶段完成后都要及时提交代码，建立清晰的版本历史，便于追溯和回滚。

**提交规范**：
1. **阶段提交**：每个五阶段开发流程完成后都要提交 Git
2. **本地提交**：只进行 `git commit`，无需 `git push`
3. **历史保护**：不能变更已提交的 commit 历史，回滚只能通过 `git revert` 或重写代码再次提交

**实施方法**：
阶段1：需求理解 → git commit -m "feat: 完成需求理解阶段"
阶段2：开发 → git commit -m "feat: 完成核心功能开发"
阶段3：测试 → git commit -m "test: 完成功能测试验证"
阶段4：总结收尾 → git commit -m "docs: 完成项目总结收尾"
阶段5：归档 → git commit -m "docs: 完成项目归档"

**约束说明**：
- ✅ **只提交不推送**：避免污染远程仓库，保持本地开发的灵活性
- ✅ **保护历史**：通过 `git revert` 回滚，确保历史记录的完整性和可追溯性
- ✅ **提交粒度**：每个阶段一个提交，便于定位问题和回滚到特定阶段

**为什么重要？**
- 📝 **可追溯性**：清晰的提交历史便于定位问题和理解代码演进
- 🔄 **安全回滚**：保护历史记录确保任何修改都可安全撤销
- 🧩 **模块化开发**：阶段化提交支持更精细的版本管理
- 🚀 **开发节奏**：强制性的阶段提交促进更规范的工作流程

## 常见问题与解决方案

### 问题1：AI 误解用户需求

**现象**：
```
用户：帮我把 URL 保存到 d:/abc/test/ 目录
AI：保存到了默认目录，忽略自定义路径
```

**原因分析**：
- 需求约束不清晰
- AI 默认使用了常见做法
- 没有确认理解

**解决方案**：

✅ **预防措施**：
1. 在需求理解阶段，QAgent 主动复述需求
2. 用户确认或调整
3. 在 SKILL.md 中明确参数提取规则

✅ **补救措施**：
1. 发现问题后立即指出
2. 明确说明期望行为
3. 要求 AI 修正

---

### 问题2：需求频繁变更

**现象**：
```
用户：实现功能A
AI：已实现 ✓
用户：改成功能B
AI：已修改 ✓
用户：还是A好，改回来
AI：...
```

**原因分析**：
- 需求理解不充分就开始开发
- 未进行方案讨论和确认

**解决方案**：

✅ **流程改进**：
1. 需求理解阶段充分讨论
2. 给出多个方案供用户选择
3. 用户确认后再开始开发

✅ **需求确认清单**：
```
- [ ] 目标明确
- [ ] 输入输出清晰
- [ ] 边界条件已知
- [ ] 技术方案确认
- [ ] 优先级明确
```

---

### 问题3：上下文超限

**现象**：
批量处理大量文档时，AI 报错或输出截断

**原因分析**：
一次性加载所有数据到上下文，超出模型限制

**解决方案**：

✅ **技术方案**：
采用流式处理（逐个文件读写）

✅ **预防措施**：
在 SKILL.md 中明确文档规模限制：
```
适用场景：
✅ 适合：几十到几百页文档
❌ 不适合：上万个文档
```

✅ **错误处理**：
当检测到批量处理风险时，QAgent 主动提醒：
```
"检测到文档数量 > 50，
 建议采用流式处理（逐个文件读写），
 是否继续批量处理？"
```

---

### 问题4：代码重复执行

**现象**：同一命令被执行多次，导致资源浪费

**原因分析**：
终端启动慢，系统重复触发

**解决方案**：

✅ **流程改进**：
1. 执行命令后等待 3-5 秒
2. 检查预期文件是否已生成
3. 如已存在则跳过重复执行

✅ **实现示例**：
```python
def safe_command(cmd, output_file):
    if os.path.exists(output_file):
        print(f"[跳过] {output_file} 已存在")
        return
    time.sleep(3)  # 等待终端启动
    execute(cmd)
```

---

### 问题5：上下文混乱和输入性错误

**现象**：
```
用户：开始新项目，基于之前的配置
AI：使用了错误的路径、过期的约束、历史的设计决策
结果：新项目从一开始方向就不对
```

**原因分析**：
- 上一项目的总结收尾阶段不完整，残留了临时信息
- 多个项目并行时，上下文相互混淆
- 用户直接基于"记忆"而非"归档文档"提需求

**解决方案**：

✅ **流程要求**：
1. 每个项目完成总结收尾阶段，明确结项
2. 下一项目开始时，QAgent 主动要求提供上下文
3. 项目间的依赖通过文档传递，而非记忆

✅ **总结收尾清单**：
```
项目结项检查：
- [ ] 交付清单明确
- [ ] SKILL.md 文档更新
- [ ] 环境配置归档
- [ ] 约束条件整理
- [ ] 上下文清理声明
```

✅ **新项目开始**：
```
QAgent：检测到开始新项目。
当前项目归档信息：
- 上一个项目：Wiki 知识库构建（已完成）
- 环境配置：Python 3.8+，依赖包清单见 docs/
- 约束说明：适合 50-500 页文档

请确认：
1. 新项目的目标
2. 是否复用上一个项目的环境
3. 新项目的约束和边界

这样可以确保我们基于干净的上下文开始。
```

### 案例1：Wiki 知识库构建项目

**项目背景**：从 Confluence 提取文档，构建本地知识库并提供语义检索

**开发流程**：

#### 阶段1：需求理解
- 用户目标：保存 Wiki 页面为本地知识库
- 上下文：需要支持语义检索
- 约束：文档规模几十到几百页

#### 阶段2：开发
- **子需求1：下载功能**
  - 方案对比：HTML 爬取 vs REST API
  - 决策：选择 REST API（更可靠）
  - 实现：单页面下载

- **子需求2：子页面递归**
  - 方案对比：递归 vs BFS
  - 决策：先实现递归（简单）
  - 问题发现：深度不可控

#### 阶段3：测试
- 测试子需求2
- 发现问题：递归深度无限制
- 触发子需求的递归流程

- **子需求2的子需求：深度控制**
  - 阶段2：重构为 BFS 算法
  - 阶段3：测试验证深度控制有效
  - 阶段4：总结：记录递归转 BFS 的原因
  - 阶段5：归档：保存 BFS 实现经验

- **继续子需求2的其他部分**...

#### 阶段4：总结收尾
- 更新 SKILL.md
- 提炼关键技术决策
- 用户确认验收

#### 阶段5：归档
- 代码归档
- 文档归档
- 知识归档（总结本文档）

**关键收获**：
- 递归模型适用于复杂需求拆解
- 及早测试可以发现问题
- 技术方案对比有助于决策
- 知识沉淀对复用很重要

## 总结

### AI 协同开发的关键成功因素

1. ✅ **清晰的沟通** - 用户提供明确的需求和反馈
2. ✅ **递归的思维** - 大需求拆解为小需求，逐个击破
3. ✅ **持续的测试** - 每个阶段都验证，及早发现问题
4. ✅ **深度的参与** - 用户不只是提需求，而是全程协作
5. ✅ **系统的沉淀** - 记录决策、经验、最佳实践

### 五阶段递归模型的价值

- **可控性**：每个阶段都有明确目标
- **可追溯**：问题可定位到具体阶段和子需求
- **可复用**：标准流程适用于任何项目
- **可优化**：每个环节都可以持续改进

### 给用户的建议

1. **投入时间在需求理解** - 开始前充分讨论，减少返工
2. **保持开放的沟通** - 及时反馈问题，不要积累
3. **尊重 AI 的能力边界** - 充分利用 AI 的优势，关键决策由人做
4. **重视知识沉淀** - 每个项目都有价值，值得记录和传承
5. **持续学习优化** - 总结经验，改进流程
